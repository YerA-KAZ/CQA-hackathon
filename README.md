# TEAM : Новое название
CQA FREEDOM BROKER

Прототип контроля качества чатов и звонков. FastAPI загружает диалоги и отдаёт интерфейс, Ollama локально оценивает каждый критерий, SQLite хранит оценки, апелляции и версии чек-листа.

## Запуск на Windows

Установите Python 3.11 или новее и проверьте в PowerShell, что `py --version` выводит нужную версию. Для первого запуска нужен доступ к PyPI. Если скачиваете проект через Git, потребуется доступ к репозиторию. Из распакованного архива можно запустить проект без Git.

Дважды нажмите `start.bat` в папке проекта или выполните `.\start.bat` в PowerShell. При первом запуске скрипт создаст окружение, установит зависимости и скопирует `.env.example` в `.env`. Когда Uvicorn запустится, откройте [интерфейс CQA](http://127.0.0.1:8000) или [документацию API](http://127.0.0.1:8000/docs). Для остановки нажмите Ctrl+C в окне сервера.

### Импорт и оценка диалогов

1. Для импорта вставьте в `CQA_API_URL` в файле `.env` полный действующий подписанный URL API, выданный организаторами, со всеми параметрами подписи. Выберите группу `DEV` или введите выданный `group_id` контрольной выборки.
2. Для оценки установите и запустите [Ollama](https://ollama.com/download). В PowerShell выполните `ollama pull qwen3.5:4b`. Эта модель указана в `.env.example`. Команда `ollama list` покажет, что модель доступна. Если используете другую модель, укажите её точное имя в `OLLAMA_MODEL`. Адрес Ollama по умолчанию — `http://127.0.0.1:11434`.
3. После изменения `.env` перезапустите сервер. Для проверки откройте интерфейс, загрузите `DEV`, выберите один диалог и нажмите «Оценить».

Интерфейс и документация API открываются сразу после запуска. Для импорта нужен доступ к API организаторов, а для новой оценки — работающая Ollama с выбранной моделью.

### Ручной запуск

Если проект уже распакован, откройте PowerShell в его корневой папке и начните с `py -m venv .venv`.

```powershell
git clone https://github.com/YerA-KAZ/CQA-hackathon.git
Set-Location CQA-hackathon
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
.\.venv\Scripts\python.exe -m uvicorn app.api:app --env-file .env
```

У приложения нет авторизации. Для локального запуска оставьте адрес привязки `127.0.0.1`.

### Проверка в интерфейсе

1. Загрузите группу DEV и выберите диалог.
2. Нажмите «Оценить». Оценка идёт в запросе последовательно по критериям. Дождитесь результата.
3. Откройте реплику-доказательство. Для звонка можно перейти к этому моменту записи.
4. Подайте апелляцию на критерий и сохраните решение с причиной. Исходный вердикт останется в карточке.
5. Измените критерий через поля редактора или в режиме JSON и примените чек-лист. Таблица покажет изменившиеся итоги. Применение пересчитывает все загруженные диалоги и использует кэш неизменённых критериев.

Для чистого прогона можно задать отдельный `CQA_DB_PATH` в `.env` и перезапустить сервер. Данные и база по умолчанию находятся в игнорируемой папке `data/`. Подписанные ссылки и ручную разметку храните вне Git.

## Метрики на ручной разметке

Сохраните независимую разметку в `data/reference.json`. Пример с вымышленным ID и несколькими критериями.

```json
[
  {
    "conversation_id": "fixture-1",
    "language": "KZ",
    "answers": {"01": "yes", "02": "n/a", "04": 15, "08": "no"}
  }
]
```

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_metrics.py --reference data/reference.json
```

По умолчанию скрипт сравнивает исходные ответы модели. Флаг `--final` учитывает решения по апелляциям. Отчёт содержит разбивку по языкам и критериям, точное совпадение, среднее абсолютное отклонение по шкале и TP/FP/FN для N/A и флага 08. Пропущенные ответы снижают долю точных совпадений и отдельно учитываются в `missing`. Они исключены из отклонения по шкале и подсчёта TP/FP/FN.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты используют синтетические диалоги, ответы модели и API. Спорные правила описаны в `app/config/assumptions.json`. Шаблоны событий предварительные. Для модели ещё нужно измерить качество на RU, KZ и EN и время прогона десяти диалогов.

## Результаты для сдачи

Используйте запущенную Ollama, заполненный `.env` и фактическое название команды. Скрипт оценивает официальный набор по исходному чек-листу из восьми критериев. Оценки из интерфейса и решения по апелляциям в этот прогон не входят.

```powershell
.\.venv\Scripts\python.exe -m scripts.generate_results dev --group-id DEV --team "Название команды"
.\.venv\Scripts\python.exe -m scripts.generate_results prod --group-id "ID от организаторов" --team "Название команды"
```

DEV должен содержать 60 чатов и 5 звонков, PROD — 10 чатов. Сохраняйте ID без изменений. Скрипт проверяет число и уникальность записей, нумерует доказательства с единицы и сохраняет неудачные оценки со статусом `error`. Файл появляется после обработки всего набора. Замерьте время прогона заранее.

Проверьте оба файла перед отправкой. Обоснования генерирует модель, поэтому проверьте их на персональные данные и подписанные ссылки. В Git добавляйте только два файла результатов и код проекта.

```powershell
git add -- results/dev/results.json results/prod/results.json
git commit -m "Add hackathon evaluation results"
git push origin main
```

Для параллельного прогона DEV используйте одинаковую версию проекта, название команды и модель Ollama. Напарник запускает часть на 43 диалога, второй участник запускает часть на 22.

```powershell
# Напарник, 43 диалога
.\.venv\Scripts\python.exe -m scripts.generate_results dev --group-id DEV --team "Название команды" --part 1 --first-count 43
# Второй участник, 22 диалога
.\.venv\Scripts\python.exe -m scripts.generate_results dev --group-id DEV --team "Название команды" --part 2 --first-count 43
```

Когда обе части готовы, положите `data/dev-part-1.json` и `data/dev-part-2.json` в папку `data/` на одном компьютере и запустите:

```powershell
.\.venv\Scripts\python.exe -m scripts.generate_results dev --merge
```

Объединение проверит обе части и создаст `results/dev/results.json`.
